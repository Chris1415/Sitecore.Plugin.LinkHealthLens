## Fixture provenance audit (rule 30 / rule 40) — THE HEADLINE

### What is genuinely good

Nine test files read **real tenant captures** from `project-planning/captures/` rather than inventing
shapes, and the captures carry provenance headers (tenant, date, endpoint, HTTP status, credential).
`reconcileAnchors.test.ts` matches the extractor **pairwise against an independent raw DOM query**
over the real Zephira Home capture, and carries a deliberately-mismatched control that must fail.
`wordBan`, `prohibition-gates` and `verify-poc` each pair every detector with a **planted violation
control**. That is rule-88-shaped discipline and it is real.

### F1 — MAJOR — `resolveLiveState.test.ts` still carries the exact fixture shape C2 was raised for

- **Files:** `site/lib/scan/resolveLiveState.test.ts:44`, `:60`
- **Fixture:** `query.mockResolvedValueOnce({ status: 404 } as never)` and `{ status: 200 }`
- **Real shape:** `node_modules/@sitecore-marketplace-sdk/client/dist/types.d.ts:3` —
  `QueryStatus = 'idle' | 'loading' | 'error' | 'success'`; `BaseQueryResult.status: QueryStatus`
  (line 24). A **numeric** top-level `status` is a value the SDK cannot produce. The HTTP code lives
  on the hey-api envelope at `res.data.response.status`.
- **Why this survived:** `/code-review` M1 rewrote the fixtures in `getLivePageState.test.ts` but did
  not sweep the **composition-level** test one layer up. `resolveLiveState` is the function that
  actually decides `published` / `unpublished` / `not-found-or-unpublished` / `could-not-check`, so
  this is the more consequential of the two files.
- **Why it still passes:** `getLivePageState.ts`'s `httpStatusOf()` carries a tolerance —
  `statusOf(envelope) ?? statusOf(res)` — whose second arm exists only to read a top-level numeric
  status. Its comment justifies it as "a fallback for hosts that surface a numeric status one level
  up"; per the `.d.ts` no such host is typeable. Fixture and tolerance are a **self-consistent
  pair** — precisely the M1 mechanism, surviving in a second place.
- **Mutation check (run, then restored — `git diff` clean):** both fixtures swapped to the real
  `.d.ts`-derived envelope (`{ data: { error: {...}, response: { status: 404 } }, status: "success" }`)
  and **all 5 tests still passed**. So this is **not** a live defect — behaviour is correct on both
  shapes. It is a **provenance violation**: the assertions prove the tolerance arm, not the real
  path, and the real 404 envelope is unexercised at the deciding layer.
- **Recommended:** move both fixtures to the real shape (proven to pass), then delete the
  `?? statusOf(res)` arm and confirm the suite stays green — if it does, that arm was dead code
  keeping a fictional fixture alive.

### F2 — MAJOR — `checkLiveViaEdge` is the lead for the headline feature and has **no capture behind it at all**

- **Files:** `site/lib/sdk/checkLiveViaEdge.ts`, `checkLiveViaEdge.test.ts`
- The **envelope depth** is correctly `.d.ts`-derived post-C1 —
  `xmc/dist/xmc/src/client-content/types.gen.d.ts:40-60` confirms `GraphqlResponses[200]` is
  `{ data?: { [key: string]: unknown }, errors?: [...] }` with `errors` a **sibling** of `data`.
  `unwrapGraphqlResponse` matches it. **That half is sound.**
- **What is not sourced:** the GraphQL `data` payload is typed `{ [key: string]: unknown }`, so the
  `.d.ts` says nothing about its *content*. Every fixture asserting
  `{ data: { data: { item: {...} } } }` is therefore **hand-written**. There is **no capture** of
  `xmc.live.graphql` or `xmc.authoring.graphql` anywhere in `project-planning/captures/` — all 12
  captures are `ai-agent-api` REST.
- **The source file concedes the transport is unproven.** Its own `catch` comment:
  *"Untested in-app per probe (b) ('two out-of-band endpoint forms rejected the raw context id') — a
  transport failure here is expected to be live, not exceptional."* So the app's **headline
  published/unpublished check** rests on a lead whose transport has never succeeded once, with
  fixtures nothing independent backs.
- **Additional untested risk (rule 85):** the query is `item(path: $path, language: $language)` with
  a **CM content path** (`/sitecore/content/Zephira-Brand/Zephira/Home/destinations`). Live and
  preview Edge diverge on route-path form; whether live Edge resolves an item by that path form is
  unverified, and a preview-side agreement would prove nothing.
- **Consequence:** US-3 / AC-3.1 / AC-3.2 cannot be called verified. The fail-closed direction from
  C2 means the worst case is an honest `could-not-check` rather than a false "published" — the design
  is defensive — but *that the feature works at all* is unevidenced.

### F3 — MAJOR — the test named "measures M3" cannot measure M3, in either direction

- **File:** `site/lib/scan/attributionRate.real.test.ts:102-116`
- It asserts `expect(rate.numerator).toBe(0)` / `expect(rate.rate).toBe(0)` — pinning **0%** against
  a **>= 50%** success threshold. The comment is honest about why (it runs `classifyFindings` only,
  never `resolveInternalFindings`, so `targetItemId` is null **by construction**).
- But the sibling test at `:58` that *does* run the full pipeline stubs `xmc.authoring.graphql` to
  return a **HIT every time** (`RESOLVED-PAGE-${n}`), which makes the rate **100% by construction**.
- So M3 is bracketed by one test that is structurally 0 and one that is structurally 100, and
  **measured by neither**. The title asserts a gate that does not exist (rule 88: a check that cannot
  fail). At minimum the title should state what it pins; the real measurement needs the tenant.

### F4 — MINOR — 55 `as never` casts across the test suite

`as never` is what lets a type-invalid fixture compile. Legitimate for partial SDK envelopes, but it
is also the mechanism by which F1 stayed invisible to `tsc`. Each one is a place the compiler was
told to stop checking. Worth a sweep for the SDK-boundary ones specifically.

### F5 — MINOR — the only two `// source:` citations in the repo point at the POC, not at an SDK

`grep` for `// source:` returns exactly two hits, both in `lib/panel/copy.ts` citing `panel.js`. No
fixture file carries the citation rule 30 requires. Provenance currently lives in prose headers
(good, and better than nothing) rather than in the greppable form the rule specifies.

## Accessibility

Static / jsdom analysis only.

- **Verified:** disclosure pattern (`aria-expanded` + `aria-controls`) on every group header; verdict
  in a polite live region; severity never colour-alone (glyph **and** text chip on every tone); every
  glyph an `aria-hidden` `<svg>`, never an emoji codepoint (asserted in both the app and the POC).
- **Gaps.** No `axe` / `jest-axe` dependency — there is **no automated a11y rule sweep at all**.
  **No runtime contrast assertion anywhere:** zero `getComputedStyle` reads in the suite. Per this
  role's standing rule, `toHaveClass("bg-primary")` passes even when `--primary-foreground` collapses
  onto `--primary`; the app uses vendored Blok, and the Blok Nova preset has shipped that way.
  **Contrast is therefore unverified in both themes.**
- **Needs the live frame:** real keyboard traversal, focus visibility, SR announcement of the live
  region, and contrast at the panel's actual width (NFR-4).
