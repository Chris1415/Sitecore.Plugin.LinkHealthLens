## 4. AC-3.3 — which path actually fires, and whether the condition holds

TR-4 built a two-leg mechanism (`resolveLiveState.ts`), not the single ambiguous call probe (b) evaluated:

1. **Lead** — `checkLiveViaEdge.ts` queries live Edge (`xmc.live.graphql`) for the already-confirmed-to-exist item. If reachable, the result is **decisive**: present means published, absent means unpublished. These are the genuinely distinct AC-3.1 states — the merged label does **not** fire on this path.
2. **Fallback** — only entered when the lead itself cannot be reached (`ok: false` — no context id, transport failure, or a GraphQL error). Here `getLivePageState`s bare 404 is used, which cannot distinguish "not live" from "wrong params" (probe (b)s original finding), so the merged not-found-or-unpublished label fires.

**The open fact, unresolved by anything on disk:** whether the lead is reachable in production. The leads own source comment (`checkLiveViaEdge.ts` line 49) states it is **"untested in-app per probe (b)"** — the out-of-band probe tried two forms of the raw context id against the live Edge endpoint and **both were rejected** ("Failed to find tenant", "No sitecore context"). No fixture on disk shows `xmc.live.graphql` succeeding through the portal bridge specifically (as opposed to out-of-band). If the in-portal call fails the same way the out-of-band ones did, the lead is `ok: false` on every call and the app falls back to the fallback path on every scan — meaning AC-3.3s merged label fires **unconditionally in practice**, exactly as it was pre-committed to before TR-4s mechanism existed.

**Verdict: unverified, not confirmed either way.** T034s real-tenant smoke is the only thing that resolves this — watching the console (`resolveLiveState`s branch) against a known-unpublished page settles it in one run. Recorded as **conditional** in § 10a, not flipped to `covered`.

## 5. The known-bad smoke page produces zero findings from the string checks — and that is arithmetic, not broken

`smoke_page_known_bad = /sitecore/content/Zephira-Brand/Zephira/Home` (T001 preflight). ADR-0009s probe measured this exact page: **57 anchors, 56 relative, 1 anchor-only fragment, 0 absolute.** Given that shape:

- `insecure-scheme` (AC-4.1) cannot fire — there is no absolute `http://` anywhere on the page.
- `malformed` (AC-5.1/5.2) cannot fire on the fragment anchor — a bare `#` is the exempt case (AC-5.2).
- There are no external rows at all, so `reachability-not-checked` never appears either.

So **the string-check axis alone currently returns the same "clean" result on the known-bad page as it would on the known-good control** — both are string-clean by construction, independent of whether either page is actually "bad" in the sense the smoke exists to catch.

TR-4 added two checks that genuinely could distinguish them: **existence** (`resolveInternal`) and **publish state** (`resolveLiveState`, § 4). Whether either of those fires on Zephira Homes real, known defects — which per T001s own note are **live route-path divergences (rule 85)**, i.e. defects that may be invisible to a CM-side checker regardless — is **not established by anything on disk**. No T034 smoke has run.

**This is a real, stated gap, not papered over:** if neither the existence nor publish-state check fires on the known-bad page either, M4s control (Koven, expected 0) and the M5/M4 smoke against Zephira would currently produce the **same zero-finding result on both pages**, and the smoke plan would prove nothing about content quality — only that both pages string-parse cleanly. This is the operators call: either accept that Zephira Homes specific defect class (live route-path divergence) is out of this checkers reach by design (in which case the known-bad page needs to be re-picked to one with a genuine CM-side defect — missing/unpublished target, malformed href, insecure scheme), or run T034 first and see what actually fires before deciding.
