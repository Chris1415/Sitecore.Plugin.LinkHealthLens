## (a) CONFIRMED — the endpoint returns real rendered HTML

`GET /api/v1/pages/{pageId}/html?language=en` → **200**, body `{ pageId, html }`, matching the declared
`Agent.PageHtmlResponse`. The `html` is a complete `<!DOCTYPE html>` document with `<head>`, preloaded
media URLs and full markup. **A1 is confirmed empirically, not merely from the type**, so the
extraction design stands and G9's widened refutation radius does not fire.

Measured on Zephira Home: **57 anchors, 20 distinct.**

## (b) AMBIGUOUS — and ambiguity here is a refutation in practice

`GET /api/v1/pages/{pageId}/live?language=en` returned **404 for BOTH** Zephira Home and Koven Home.

Two pages, two 404s, and **nothing in the response distinguishes** *"this page is not live"* from
*"this endpoint/params combination does not resolve"*. The body is a bare RFC-7231 `Not Found`. Since
US-3's whole value is telling those two apart, a signal that cannot be told apart from a wiring error
is not a signal.

**Consequence:** **AC-3.3 fires** — the merged `not found or not published` label is the honest
output, exactly as it was pre-committed for this case. US-3 degrades rather than mislabelling.
Resolving this properly needs a page **known** to be published on this tenant as a control, which we
do not currently have.

## (c) CONFIRMED, and it exposes the blocking defect

`GET /api/v1/sites` → **200**, 7 sites with `{ id, name, targetHostname, rootPath }`.

**`targetHostname` is empty on 0 of 7 — every single site.** That is the finding, not a footnote: it
is what makes (e) unusable.

## (e) REFUTED — `path-by-url` cannot resolve this app's links

Two independent reasons, either sufficient:

1. **It resolves by hostname → site.** `https://zephira.example/destinations` → **404**
   `"No matching site found for hostname: zephira.example"`. With no `targetHostname` configured on
   any site, **nothing on this tenant can match**.
2. **It requires an absolute URL, and the app's input is relative.** A relative path returns **400**
   `"Input should be a valid URL, relative URL without a base"`. Measured on the real page:
   **56 of 57 anchors are relative** (`/book`, `/destinations/Accra`, `/book?to=Lisbon`), 1 is
   anchor-only (`#content`), and **zero are absolute**.

So the endpoint ADR-0008 built the classification on cannot be called with what the page actually
contains, on a tenant whose sites carry no hostnames.

### The alternative — PROVEN, not proposed

Resolve the site-relative href against the site's content tree by **path**, via Authoring GraphQL:

```
/sitecore/content/Zephira-Brand/Zephira/Home/destinations  → HIT  e5ecb5f7ad3d489d8a48b9d9148e410b (Page)
/sitecore/content/Zephira-Brand/Zephira/Home/no-such-page  → MISS
```

That is precisely the exists / not-found distinction US-1 needs, with **no hostname involved**. It is
available in-app: **`xmc.authoring.graphql`** is a declared SDK key, so this works through the portal
bridge and does not require Mode B or a backing route — ADR-0002 is untouched.

Open sub-questions this alternative inherits: the site root must be derived (`sites[].rootPath` gives
it — Zephira's is `d3c70fca-...`, the same id as its Home), and query strings / fragments must be
stripped before lookup (`/book?to=Lisbon` → `/book`).

## (f) CONFIRMED — but by landmarks, and that is a property of the head app

No `data-component` / `data-placeholder` / `data-sc-*` attributes exist in the HTML. **The structural
signal is semantic HTML landmarks:**

| element | anchors inside |
|---|---|
| `<header>` | 6 |
| `<nav>` | 4 |
| `<footer>` | 4 |
| `<main>` | 49 |

Chrome and content are cleanly separable, so **ADR-0006's structural `origin` survives** and M3 does
not collapse into the unfailable metric that ADR-0006 exists to prevent.

**The caveat is real and belongs in the ADR:** this is a property of the **rendering app**, not of the
SDK. It holds because Content SDK's `Layout.tsx` emits landmarks. A head app that renders `<div>`s
instead would return the signal to absent, and the three-way label would lose its basis on that site.

## (d) and (g) — NOT CAPTURED, and (g) is the one that matters

Both need the app framed by an authenticated Cloud Portal Pages canvas; Mode A has no mock-client
path. **(g)** asks whether any field-level selection exists. The declared surface says no —
`MutationMap['pages.context']` takes `PagesContextParams { itemId?, language?, itemVersion? }` and
`pages.reloadCanvas` takes `params: void`. If the live surface agrees, **AC-7.1 and AC-7.4 describe a
capability that does not exist**, and shipping item-level navigation labelled *"Jump to field"* is
forbidden by the plan.
