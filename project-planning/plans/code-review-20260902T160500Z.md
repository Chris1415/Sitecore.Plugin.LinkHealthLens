## Critical

### C1 — GraphQL `errors` is read one level too deep; every error branch is dead, and an errored query is reported to the editor as "Target not found"

- **Files:** `site/lib/sdk/resolveItemByPath.ts:51`, `site/lib/sdk/resolveItemPathById.ts:42`,
  `site/lib/sdk/checkLiveViaEdge.ts:41`
- **Category:** correctness · SDK contract (rule 40) · `marketplace-sdk-xmc` § 6c (declared CRITICAL)
- **Evidence:** `node_modules/@sitecore-marketplace-sdk/xmc/dist/xmc/src/client-authoring/types.gen.d.ts`
  → `Authoring.GraphqlResponses[200] = { data?: {…}, errors?: […] }`. `errors` is a **sibling** of
  `data`. All three call sites compute `root = res.data.data` (correct for the payload) and then test
  `root.errors` — a key that never exists there.
- **Why it matters:** the branch is unreachable, so a GraphQL failure (permissions, schema drift, a
  bad path) falls through to `!root` / `item == null` and returns `{ ok: true, found: false }`. The
  panel then tells the editor **"Target not found — No item in the CM matches this path."** about a
  link nobody checked. That is precisely the false-positive class the PRD's `could-not-check`
  member exists to prevent, and it is indistinguishable from a real finding in the UI.
  `checkLiveViaEdge` has the same defect on the published/unpublished axis.
- **Fix applied:** new `site/lib/sdk/graphqlEnvelope.ts` owns the depth once
  (`unwrapGraphqlResponse`); all three call sites use it; a missing/unrecognisable body is now a
  reported failure, never a miss.

### C2 — `getLivePageState` reads the HTTP status off the wrong object; the unpublished fallback fails OPEN and reports every page as published

- **File:** `site/lib/sdk/getLivePageState.ts:26-33, 51-57` (pre-fix)
- **Category:** correctness · SDK contract (rule 40)
- **Evidence:** `node_modules/@sitecore-marketplace-sdk/client/dist/types.d.ts` →
  `QueryStatus = 'idle' | 'loading' | 'error' | 'success'`; `BaseQueryResult.status: QueryStatus`.
  It is **never** an HTTP code. `client.query` (`dist/index.esm.js`) catches every rejection and
  resolves `{ data, error, status: 'error', isError: true }`, and the XMC module returns the hey-api
  result unchanged — so the HTTP code lives at `res.data.response.status`.
- **Why it matters:** `statusOf(res)` therefore returned `undefined` for **every** resolved outcome,
  and the function fell through to `return { ok: true, live: true }`. A 404 (the one signal the
  fallback exists to detect), a 500, and a hard SDK failure were all reported as **published**. This
  is the app's headline check, and it failed in the direction that produces a confident, wrong,
  reassuring answer. It is only masked because `checkLiveViaEdge` runs first — but that lead is
  itself documented as "expected to fail live" (probe (b)), which is exactly when this fallback runs.
- **Fix applied:** `httpStatusOf()` reads `res.data.response.status` (falling back to the
  QueryResult for hosts that surface a numeric status one level up). An undeterminable status now
  **fails closed** to `request-failed` → `could-not-check`, never "published"; a payload with no
  error beside it is still accepted as live so a genuine 2xx is not downgraded.

## Major

### M1 — Test fixtures encode the same misunderstanding as the code, which is why 264 green tests could not see C1 or C2

- **Files:** `site/lib/sdk/resolveItemByPath.test.ts:65`, `site/lib/sdk/getLivePageState.test.ts:21,30,49`;
  `site/lib/sdk/checkLiveViaEdge.test.ts` (no error case at all)
- **Category:** test quality
- **What is wrong:** `resolveItemByPath.test.ts:65` mocks `{ data: { data: { errors: [...] } } }` —
  `errors` nested *inside* `data`, the shape the SDK never produces. The test passed, and it proved
  only that the code and the fixture agreed with each other. `getLivePageState.test.ts` puts a
  numeric `status` at the top level of the QueryResult, where the type says a string lives; the
  "404 → unpublished" and "500 → request-failed" tests both passed against code that could not
  reach either branch. `checkLiveViaEdge` had no GraphQL-error test whatsoever.
- **Why it matters:** this is the mechanism by which a 264-test build shipped four live defects the
  operator found by looking at the screen. A fixture invented alongside the code cannot falsify it;
  only a fixture derived from the `.d.ts` or a capture can.
- **Fix applied:** all fixtures rewritten to the shapes declared in `types.gen.d.ts` /
  `types.d.ts`; added the partial-payload-with-errors case, the unrecognisable-envelope case, the
  fail-closed case, and the missing `checkLiveViaEdge` error case. Both fixes were
  **mutation-checked** — reverting the errors depth and reverting `httpStatusOf` each fail the suite.

### M2 — The scaffold demo surface shipped: an undeclared route rendering the whole `application.context`, plus the `as string` context-id cast

- **Files:** `site/app/page.tsx`, `site/components/examples/built-in-auth/application-context.tsx`,
  `site/components/examples/built-in-auth/with-xmc/list-languages.tsx:33`
- **Category:** security · scope discipline · `additions.review_checks` (extension-point usage)
- **What is wrong:** ADR-0004 declares **one** extension point (`xmc:pages:contextpanel`, route
  `/pages-context`). The build also shipped `/`, rendering `JSON.stringify(appContext, null, 2)` —
  which contains both the `live` and `preview` `sitecoreContextId` for the tenant — into the DOM,
  plus `console.log("languages from client", …)` of raw SDK responses. `list-languages.tsx:33` uses
  `appContext?.resourceAccess?.[0]?.context?.preview as string`, the exact anti-pattern
  `marketplace-sdk-xmc` § 6a names ("treat the cast as a post-scaffold edit, not a template").
- **Why it matters:** a context id is a tenant-scoped delivery credential, and a Marketplace app is
  publicly hosted. Even behind the iframe handshake, a second undeclared surface whose only purpose
  is to print credentials is not something to ship. The cast is a Critical-severity pattern in the
  skill's own terms and would have been caught had the brief been resolved.
- **Fix applied:** `components/examples/` deleted (no product code imported it); `app/page.tsx`
  replaced with a static orientation line. Build now emits `/`, `/_not-found`, `/pages-context`.

### M3 — `MarketplaceProvider` has no failure path for `application.context`; the panel goes permanently blank with no message

- **File:** `site/components/providers/marketplace.tsx:37-46` (pre-fix)
- **Category:** correctness · NFR-2 ("never blank the panel")
- **What is wrong:** the effect handles only `if (res?.data)`. No `.catch`, no else. If the query
  rejects or returns an empty context, `appContext` stays `null`, `loading` is already `false` and
  `client` is set — so the provider hits `if (!appContext) return null` and renders **nothing**,
  forever, with no error and no retry. Also `console.log("appContext", res.data)` prints both
  context ids to the host console.
- **Fix applied:** added the rejection and empty-response branches (both set the provider's existing
  error UI) and a cancellation guard; removed the context log.

### M4 — The page HTML is re-parsed twice per anchor; ~300 full `DOMParser` passes on a 150-anchor page against a 6s budget

- **Files:** `site/lib/scan/classifyFindings.ts:20-38`, `classifyOrigin.ts:23`, `attribute.ts:96-99`,
  `anchorCheck.ts:14`
- **Category:** performance
- **What is wrong:** `classifyFindings` maps over findings and calls `classifyOrigin` (which parses
  the whole document) and `attribute` (which parses it again *and* re-`JSON.parse`s
  `presentationDetails`) once per finding. `checkInPageAnchor` adds a third parse for every
  fragment href. Success criterion M1 is "worst observed ≤ 6s across pages of ≤ 150 anchors" —
  this is quadratic-ish work against exactly that ceiling, on the main thread, in an iframe.
- **Fix applied:** parse once per scan in `classifyFindings`; added `classifyOriginIn(doc, …)`,
  `attributeIn(doc, …, renderings)` and `checkInPageAnchorIn(doc, …)`. The string-taking wrappers
  are kept so the existing per-check unit tests still drive the same rule.

## Minor (left unfixed — for the operator)

1. **ADR-0010's probe transcript contradicts the shipped call, and the shipped call is right.**
   The ADR records `client.mutate('pages.context', { itemId: <current> })` — unwrapped. Per
   `node_modules/@sitecore-marketplace-sdk/client/dist/types.d.ts`
   (`MutationOptions<K> extends BaseMutationOptions<…, MutationMap[K]['params']>` → `params?: TParams`)
   and the minified runtime (`mutate` destructures `{ params: o }` and sends `request(op, o)`), the
   correct shape is `{ params: { itemId } }` — which is what `JumpAction.tsx:31` does. The
   unwrapped form would send `undefined` on the wire and would not typecheck. **The ADR prose should
   be corrected**, or the next reader will "fix" working code into the defect. No code change made.
2. **Prohibition gate 2 keys its allowed set by basename only.** `test/prohibition-gates.test.ts:98`
   maps `"JumpAction.tsx" → "pages.context"` and matches `path.basename(file)`, so a new
   `lib/anywhere/JumpAction.tsx` with a `pages.context` mutate would pass. Pin repo-relative paths.
   Its comment also says "one of the three allowed" while four are listed (`resolveItemPathById.ts`
   **is** correctly in the set — the gate matches reality, only the prose is stale).
3. **`app/layout.tsx` metadata is still `"Create Next App" / "Generated by create next app"`** —
   the iframe document title an editor's browser reports.
4. **Copy inconsistency on the chrome mitigation line.** `GroupList.tsx:44` renders
   `"{n} of {m} are site chrome — not fixable from this page"` while the fixed, non-negotiable
   string (and `verdict.ts:78`) is `"…not editable from this page"`. One of the two words is wrong.
5. **Eleven comment-density warnings** from `audit-comment-density.mjs` (exit 0, no walls, so rule 87
   passes). Worst: `lib/scan/attribute.ts` 62%, `lib/scan/attributionRate.ts` 106%,
   `lib/sdk/pagesGetPageHtml.ts` 59%. Several are ADR/probe narrative that now has a home in
   `docs/build-decisions.md`.
6. **`lib/scan/*` pure model code depends on the browser `DOMParser`.** Fine for a Mode A client-only
   app, but it makes `classifyOrigin` / `attribute` / `anchorCheck` untestable outside jsdom and
   couples the model layer to the DOM. Worth an injected parser if this ever grows a worker.

## Overall assessment

**NEEDS WORK** (as reviewed) → **PASS WITH ISSUES** (after the fixes above).

The panel's presentation layer, status-set model, grouping, precedence, accessibility and
prohibition gates are genuinely well built, and the two 2026-09-02 defect fixes already in the tree
(start-item resolution, navigation target) are correct and well-tested. The build's weakness is
concentrated entirely in the **SDK boundary**, and it is one shape repeated: the response envelope
was assumed rather than derived, and the tests were written from the same assumption, so the suite
confirmed the assumption instead of testing it. Both Criticals fail in the *reassuring* direction —
one accuses a healthy link, the other declares an unpublished page published — which is why 264
green tests and four human review passes did not surface them. This is the exact cost of the
unresolved pack brief.

Remaining risk the local suite cannot close: `getLivePageState`'s real 404 envelope was **never
captured in-app** (the header says so, and it is still true). The fix now fails closed rather than
open, so the worst case is an honest `could-not-check` instead of a false "published" — but the
real shape still needs one real-tenant observation before the unpublished check can be called
verified.
